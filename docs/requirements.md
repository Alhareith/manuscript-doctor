# 📋 Manuscript Doctor — متطلبات النظام

> **الغرض من الوثيقة:** تحديد ما يجب أن يفعله النظام، والقيود التي يجب أن يلتزم بها، ومعايير قبول كل وظيفة في نسخة الـMVP.
> **هذه الوثيقة تصف المتطلبات فقط؛ أما أسباب القرارات فتوجد في `docs/decisions.md`، والتصميم المعماري في `docs/architecture.md`.**

---

## 🩺 تعريف مختصر

**Manuscript Doctor** نظام ويب لتشخيص ومعالجة صور المخطوطات باستخدام تقنيات معالجة الصور التقليدية، مع التركيز على اختيار معالجة مناسبة للحالة والتحقق من أن التحسين لم يؤدِ إلى تغير بنيوي واضح في التفاصيل الأصلية.

<div align="center">

### Diagnose → Treat → Preserve → Verify

</div>

المسار الأساسي للنسخة الأولى:

```text
رفع الصورة
    ↓
التحقق منها
    ↓
فحصها وتحليلها
    ↓
تشخيص حالتها
    ↓
تقدير حساسية المعالجة
    ↓
اقتراح المعالجة
    ↓
تنفيذ المعالجة
    ↓
Preservation Verification
    ↓
المقارنة والتفسير
    ↓
تنزيل النتيجة
```

# 1. المتطلبات الوظيفية — Functional Requirements

## 1.1 رفع الصورة والتحقق منها

| المعرف    | المتطلب                                        | معيار القبول                                                     | الأولوية |
| --------- | ---------------------------------------------- | ---------------------------------------------------------------- | :------: |
| **FR-01** | فتح التطبيق من المتصفح دون تسجيل دخول.         | تظهر الصفحة الرئيسية دون خطأ.                                    | 🔴 أساسي |
| **FR-02** | رفع صورة بصيغة `JPG` أو `JPEG` أو `PNG`.       | يقبل Backend الصورة المدعومة ويعيد استجابة نجاح.                 | 🔴 أساسي |
| **FR-03** | التحقق من وجود حقل الصورة في الطلب.            | الطلب الفارغ لا يسبب انهيارًا ويعيد خطأ واضحًا.                  | 🔴 أساسي |
| **FR-04** | التحقق من أن اسم الملف غير فارغ.               | الملف دون اسم يرفض برسالة مناسبة.                                | 🔴 أساسي |
| **FR-05** | رفض الامتدادات غير المسموحة.                   | لا يقبل النظام أنواعًا خارج القائمة المسموحة.                    | 🔴 أساسي |
| **FR-06** | التحقق من أن الملف صورة فعلية قابلة للقراءة.   | الملف المزيف أو التالف يرفض حتى لو كان امتداده `.jpg` أو `.png`. |  🔴 أمان |
| **FR-07** | فرض حد أعلى لحجم طلب الرفع.                    | الطلب الذي يتجاوز الحد يرفض باستجابة مضبوطة.                     |  🔴 أمان |
| **FR-08** | فرض حد أعلى منطقي لعدد Pixels بعد فك الصورة.   | الصور ذات الأبعاد المفرطة ترفض قبل إدخالها في مسار المعالجة.     |  🔴 أمان |
| **FR-09** | إنشاء `image_id` فريد للصورة.                  | كل عملية رفع ناجحة تحصل على معرف مستقل.                          | 🔴 أساسي |
| **FR-10** | حفظ الصورة الأصلية داخل `storage/uploads`.     | تحفظ الصورة دون استخدام اسم المستخدم كاسم تخزين فعلي.            | 🔴 أساسي |
| **FR-11** | الحفاظ على البايتات الأصلية للصورة بعد التحقق. | لا تتم إعادة ترميز الصورة الأصلية قبل حفظها.                     | 🔴 سلامة |
| **FR-12** | إتاحة الصورة الأصلية بواسطة `image_id`.        | يمكن عرض الصورة دون كشف مسار الخادم.                             | 🔴 أساسي |

## 1.2 فحص الصورة — Examination

يجب أن يعمل الفحص على **الصورة الأصلية فقط** وقبل أي معالجة.

### المؤشرات الأساسية

| المعرف    | المؤشر                 | طريقة التمثيل                        | الغرض                         |
| --------- | ---------------------- | ------------------------------------ | ----------------------------- |
| **FR-13** | Dimensions             | `width`, `height`, `channels`        | وصف بنية الصورة               |
| **FR-14** | Brightness             | متوسط شدة Grayscale                  | تقدير السطوع العام            |
| **FR-15** | Contrast               | الانحراف المعياري لقيم Grayscale     | تقدير انتشار درجات الإضاءة    |
| **FR-16** | Dynamic Range          | الفرق بين `P95` و`P5`                | تقدير النطاق الفعلي للدرجات   |
| **FR-17** | Sharpness Indicator    | Variance of Laplacian                | مؤشر تقريبي لقوة الحواف       |
| **FR-18** | Noise Indicator        | فرق محلي تقريبي بعد Median smoothing | تقدير تقريبي للتغيرات المحلية |
| **FR-19** | Illumination Variation | تغير خريطة الإضاءة منخفضة التردد     | تقدير عدم تجانس الإضاءة       |
| **FR-20** | Edge Density           | نسبة Pixels المكتشفة كحواف           | تقدير كثافة البنية الحافية    |

### متطلبات الفحص

| المعرف    | المتطلب                             | معيار القبول                                                          |
| --------- | ----------------------------------- | --------------------------------------------------------------------- |
| **FR-21** | دعم صور `Grayscale`, `BGR`, `BGRA`. | يستطيع Analyzer تحليل الأنواع الثلاثة دون خطأ.                        |
| **FR-22** | عدم تعديل الصورة أثناء التحليل.     | الصورة بعد استدعاء Analyzer مطابقة للمدخل.                            |
| **FR-23** | رفض المدخل غير الصالح.              | `None` أو مصفوفة فارغة تسبب خطأ مضبوطًا وواضحًا.                      |
| **FR-24** | إعادة نتائج منظمة.                  | تعاد الأبعاد والمقاييس والتشخيص وPreservation Profile ضمن بنية واضحة. |

## 1.3 التشخيص — Diagnosis

| المعرف    | المتطلب                                     | معيار القبول                                                           |
| --------- | ------------------------------------------- | ---------------------------------------------------------------------- |
| **FR-25** | تحويل بعض المقاييس إلى تشخيصات قابلة للفهم. | يستطيع النظام إنتاج حالات مثل `dark`, `low_contrast`, `low_sharpness`. |
| **FR-26** | كل تشخيص يحتوي على `code`.                  | يستخدم Backend معرفًا تقنيًا ثابتًا.                                   |
| **FR-27** | كل تشخيص يحتوي على `label`.                 | يظهر اسم مفهوم للمستخدم.                                               |
| **FR-28** | كل تشخيص يحتوي على `severity`.              | يستخدم مستوى مثل `medium` أو `high` وفق القاعدة المحددة.               |
| **FR-29** | كل تشخيص يحتوي على `message`.               | يقدم تفسيرًا مختصرًا لما تشير إليه القياسات.                           |
| **FR-30** | فصل حساب Metric عن قاعدة التشخيص.           | يمكن تعديل Threshold دون إعادة كتابة خوارزمية القياس.                  |
| **FR-31** | استخدام Thresholds أولية قابلة للمعايرة.    | توثق الحدود بأنها مبدئية ولا تعرض كحقائق علمية نهائية.                 |

## 1.4 Preservation Profile

> **Preservation Profile** يصف مقدار الحذر المقترح **قبل المعالجة**.
> وهو مختلف تمامًا عن **Preservation Verification** الذي يحدث بعد المعالجة.

| المعرف    | المتطلب                                              | معيار القبول                                            |
| --------- | ---------------------------------------------------- | ------------------------------------------------------- |
| **FR-32** | تكوين Preservation Profile من مؤشرات الصورة الأصلية. | يعاد Profile مع نتيجة التحليل.                          |
| **FR-33** | تمثيل الحساسية بمستوى مفهوم.                         | يعاد أحد المستويات `low`, `moderate`, `high`.           |
| **FR-34** | إرجاع أسباب المستوى.                                 | يحتوي Profile على Indicators قابلة للتفسير.             |
| **FR-35** | تحديد طبيعة التقدير.                                 | يوضح النظام أن النتيجة `heuristic` وليست قياسًا مطلقًا. |
| **FR-36** | عدم تفسير Profile كضمان للحماية.                     | لا تعرض النتيجة كنسبة مؤكدة من النص المحفوظ.            |

# 4. Preservation Verification

> الهدف هو تقييم أثر المعالجة على البنية البصرية، وليس إثبات سلامة النص لغويًا.

## 4.1 المتطلبات الأساسية

| المعرف    | المتطلب                              | معيار القبول                                                        |
| --------- | ------------------------------------ | ------------------------------------------------------------------- |
| **FR-59** | مقارنة Original مع Processed Result. | لا يعمل Preservation Verification على Result منفردة.                |
| **FR-60** | استخراج Preservation Metrics.        | تعاد مؤشرات بنيوية قابلة للاختبار.                                  |
| **FR-61** | اكتشاف مؤشرات فقد أو تغير.           | يمكن للنظام إنتاج Warnings عند ظهور تغيرات غير مرغوبة.              |
| **FR-62** | تمثيل التقييم النهائي.               | يمكن للنظام استخدام حالات مثل `acceptable`, `caution`, `high_risk`. |
| **FR-63** | إظهار أن النتيجة مؤشر مساعد.         | لا تستخدم صياغة مثل `100% safe`.                                    |
| **FR-64** | عدم مساواة كل اختلاف بفقد نص.        | Structural Difference لا يفسر تلقائيًا كحرف مفقود.                  |
| **FR-65** | فصل Preservation عن Analyzer.        | مقارنة قبل/بعد تتم في وحدة مستقلة.                                  |

| المعرف    | المتطلب                                      | معيار القبول                                                |
| --------- | -------------------------------------------- | ----------------------------------------------------------- |

| **FR-68** | حفظ ترتيب الخطوات.                           | ترجع Pipeline قائمة مرتبة بما تم تطبيقه.                    |
| **FR-69** | شرح سبب كل خطوة.                             | لكل Step سبب واضح.                                          |
| **FR-70** | تمرير النتيجة إلى Preservation Verification. | لا تعتبر نتيجة Pipeline مكتملة قبل التقييم عند توفره.       |
| **FR-71** | التعامل المحافظ مع غياب التقييم.             | لا يدعي النظام أن النتيجة آمنة إذا تعذر Preservation Check. |
| **FR-72** | قابلية التطوير لتجربة Candidates مستقبلًا.   | يمكن إضافة Candidate Selection دون تغيير API الأساسي.       |

# 7. المتطلبات المعمارية — Architecture Requirements

| المعرف    | المتطلب                                                                               |
| --------- | ------------------------------------------------------------------------------------- |
| **AR-01** | `app.py` مسؤول عن Flask وHTTP والتحقق وإدارة الطلبات، وليس عن خوارزميات معالجة الصور. |
| **AR-02** | `analyzer.py` مسؤول عن فحص الصورة الأصلية والتشخيص.                                   |
| **AR-03** | `recommender.py` مسؤول عن التوصيات ولا ينفذ الخوارزميات بنفسه.                        |
| **AR-04** | `operations.py` مسؤول عن عمليات معالجة الصور المستقلة.                                |
| **AR-05** | `pipeline.py` مسؤول عن تنظيم المعالجة التلقائية.                                      |
| **AR-06** | `preservation.py` مسؤول عن مقارنة Original وResult.                                   |
| **AR-07** | JavaScript مسؤول عن التفاعل وتحديث الواجهة فقط.                                       |
| **AR-08** | Backend هو مصدر الحقيقة للمقاييس والتشخيص والتوصيات والتقييم.                         |
| **AR-09** | لا تحتوي JavaScript على Thresholds أو قواعد Diagnosis.                                |
| **AR-10** | لا يرسل العميل مسار ملف ليستخدمه Backend.                                             |
| **AR-11** | تستخدم الصور `image_id` بدل المسارات.                                                 |
| **AR-12** | تستخدم النتائج `result_id` مستقلًا.                                                   |
| **AR-13** | لا يوجد متغير عالمي باسم `current_image` أو ما يؤدي نفس الوظيفة.                      |
| **AR-14** | تستخدم العمليات Operation Registry بدل استدعاء أسماء دوال قادمة من المستخدم.          |
| **AR-15** | إضافة Operation جديدة لا تتطلب Route جديدًا.                                          |
| **AR-16** | جميع ردود JSON تستخدم البنية الموحدة.                                                 |

# 8. Preservation Architecture Requirements

| المعرف     | المتطلب                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------- |
| **PAR-01** | مقارنة الأصل والنتيجة مسؤولية منفصلة عن تحليل الصورة الأصلية.                                |
| **PAR-02** | Preservation Verification تعتمد دائمًا على `Original + Processed Result`.                    |
| **PAR-03** | نتيجة Manual Operation سابقة لا تصبح Original للعملية التالية تلقائيًا.                      |
| **PAR-04** | Preservation Warning لا تعتبر دائمًا HTTP Error.                                             |
| **PAR-05** | يمكن تمثيل Assessment بصياغة `acceptable / caution / high_risk` أو صياغة معتمدة مكافئة.      |
| **PAR-06** | Structural Difference لا تفسر تلقائيًا كفقد نص.                                              |
| **PAR-07** | Preservation Metrics قابلة للاختبار مستقلًا.                                                 |
| **PAR-08** | يمكن تطوير Pipeline لتجربة Candidates لاحقًا دون تغيير عقد API الأساسي.                      |
| **PAR-09** | فشل Preservation Check تقنيًا لا يحذف Result صالحة تلقائيًا.                                 |
| **PAR-10** | عند غياب Preservation Assessment يجب أن توضح الواجهة أن التقييم غير متاح بدل افتراض السلامة. |

| **NFR-02** | اللغة               | الواجهة عربية وتستخدم `lang="ar"` و`dir="rtl"`.                        |
| **NFR-03** | Responsive          | تعمل الواجهة على Desktop وMobile.                                      |
| **NFR-04** | سلامة عرض الصور     | تستخدم الصور `object-fit: contain` أو سلوكًا مكافئًا.                  |
| **NFR-05** | فصل المسؤوليات      | لا تتداخل مسؤوليات Flask والتحليل والمعالجة والتقييم والواجهة دون سبب. |
| **NFR-06** | تخزين Runtime       | `uploads` و`results` ملفات تشغيل مؤقتة وليست بيانات دائمة.             |
| **NFR-07** | سلامة المسارات      | لا يمكن الوصول إلى ملفات خارج المجلدات المسموحة.                       |
| **NFR-08** | حدود الرفع          | يفرض Backend حدًا للحجم وعدد Pixels.                                   |
| **NFR-09** | مقاومة الفشل        | الأخطاء المتوقعة لا تسبب انهيار التطبيق.                               |
| **NFR-10** | الحفاظ على Original | لا تكتب أي عملية على الأصل.                                            |
| **NFR-11** | قابلية الاختبار     | Analyzer وOperations وPipeline وPreservation قابلة للاختبار دون واجهة. |
| **NFR-12** | التوثيق             | الوثائق تطابق السلوك الفعلي.                                           |
| **NFR-13** | قابلية التفسير      | التشخيص والتوصيات وخطوات Pipeline يمكن شرح أسبابها.                    |
| **NFR-14** | البساطة             | لا تضاف مكتبات أو طبقات معمارية دون حاجة فعلية.                        |
| **NFR-15** | الاستقلال عن البيئة | لا تعتمد الشيفرة على مسارات شخصية ثابتة في جهاز المطور.                |
| **NFR-16** | استجابة موحدة       | أخطاء API ونجاحها تستخدم شكلًا ثابتًا.                                 |

# 11. المتطلبات الأمنية الأساسية

| المعرف     | المتطلب                                                        |
| ---------- | -------------------------------------------------------------- |
| **SEC-01** | Backend يعيد التحقق من كل طلب حتى لو تحققت الواجهة منه مسبقًا. |
| **SEC-02** | لا يستخدم اسم الملف القادم من المستخدم كاسم تخزين فعلي.        |
| **SEC-03** | تستخدم UUIDs أو معرفات آمنة مماثلة.                            |
| **SEC-04** | لا يقبل Backend عملية غير مسجلة داخل Operation Registry.       |
| **SEC-05** | لا يستطيع المستخدم تمرير اسم Python function للتنفيذ.          |
| **SEC-06** | لا يستطيع المستخدم تمرير filesystem path للوصول إلى ملف.       |
| **SEC-07** | لا يعتمد قبول الصورة على امتداد الملف وحده.                    |
| **SEC-08** | تحدد حدود لحجم طلب الرفع وأبعاد الصورة.                        |
| **SEC-09** | لا تعرض Stack Trace للمستخدم النهائي.                          |
| **SEC-10** | ملفات Runtime لا تتبع بواسطة Git.                              |

# 16. Scientific Honesty Requirements

هذه المتطلبات إلزامية في منطق النظام والواجهة والتوثيق.

| المعرف     | المتطلب                                                                      |
| ---------- | ---------------------------------------------------------------------------- |
| **SCI-01** | لا يدعي النظام أنه يعرف أن كل تفصيل مفقود كان حرفًا أو جزءًا لغويًا مهمًا.   |
| **SCI-02** | لا يدعي النظام إعادة المخطوطة إلى حالتها التاريخية الأصلية.                  |
| **SCI-03** | لا يعرض Preservation Indicator كنسبة حقيقية مؤكدة من النص المحفوظ.           |
| **SCI-04** | لا يصف Treatment بأنها الأفضل مطلقًا دون معيار مثبت.                         |
| **SCI-05** | لا يستخدم مصطلح Artificial Intelligence لوصف Rule-Based Logic.               |
| **SCI-06** | Thresholds التشخيصية الأولية توصف بأنها Heuristics قابلة للمعايرة.           |
| **SCI-07** | Metrics التقريبية مثل Noise وSharpness توصف بصفتها Indicators عند الحاجة.    |
| **SCI-08** | اختلاف Pixels لا يساوي تلقائيًا فقد معلومات.                                 |
| **SCI-09** | Preservation Verification يوصف كتقييم بنيوي مساعد، وليس كإثبات مطلق للسلامة. |

# 21. حوكمة تغيير المتطلبات

أي فكرة جديدة لا تنفذ مباشرة.

يجب أولًا الإجابة عن:

|  #  | السؤال                                                |
| :-: | ----------------------------------------------------- |
|  1  | هل تحل مشكلة حقيقية داخل Manuscript Doctor؟           |
|  2  | هل تدعم فلسفة `Diagnose → Treat → Preserve → Verify`؟ |
|  3  | هل يمكن تنفيذها بحل أبسط؟                             |
|  4  | هل ستؤثر على المعمارية الحالية؟                       |
|  5  | هل تحتاج مكتبة أو تقنية جديدة؟                        |
|  6  | هل تضيف عبئًا كبيرًا على الاختبارات؟                  |
|  7  | هل يمكن تأجيلها دون الإضرار بالـMVP؟                  |

القرار الممكن:

```text
مفيدة وضرورية الآن
        ↓
تحديث requirements
        ↓
تحديث architecture إذا لزم
        ↓
تحديث decisions
        ↓
تحديث tests
        ↓
التنفيذ
```

أو:

```text
مفيدة ولكن غير ضرورية الآن
        ↓
Optional / Future
```

> **لا تغير فلسفة المشروع الأساسية بسبب ميزة جديدة. الإضافات مسموحة، أما تغيير جوهر المشروع فلا يتم إلا بقرار صريح جديد.**
