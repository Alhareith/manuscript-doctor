## القرار

نبدأ بـ **Modular Monolith**: تطبيق Flask واحد، لكن بحدود واضحة بين الواجهة وطبقة HTTP ومحرك المعالجة والتخزين. هذا أقل تعقيدًا من الخدمات المنفصلة ويظل قابلًا لإعادة التنظيم لاحقًا.

## المكونات

`واجهة HTML/CSS/JS → Flask (app.py) → processing/ → OpenCV + NumPy → storage/`

## حدود المسؤولية

| الجزء | مسؤوليته |
| --- | --- |
| `app.py` | المسارات، التحقق من الطلب، وإرجاع الاستجابة. |
| `processing/analyzer.py` | قياسات ونتائج التشخيص. |
| `processing/operations.py` | العمليات اليدوية المستقلة. |
| `processing/pipeline.py` | ترتيب الخطوات الذكية وسبب الاقتراح. |
| `templates/` و`static/` | العرض والتفاعل فقط؛ بلا منطق معالجة. |
| `storage/` | ملفات وقت التشغيل، وليست مصدرًا دائمًا للبيانات. |

## التوسع

عند ثبوت احتياج فعلي يمكن إضافة API مستقلة أو واجهة موبايل فوق طبقة معالجة ثابتة. لا نفصل الخدمات الآن؛ لا توجد حاجة مثبتة لذلك في النسخة الأولى.

## الخطوة التالية

الالتزام بهذه الحدود عند إضافة أول سطر من الكود.
