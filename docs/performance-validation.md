# التحقق من إصلاح الأداء وتخطيط الواجهة

مرجع البداية: `master / 57af5ba`. التغييرات محلية في Working Tree؛ لا commit ولا push.

## ما قيس قبل التعديل

- شُغّل التطبيق واختُبر بالمتصفح قبل التعديل؛ حُفظت قياسات DOM ولقطات المقاسات 1440، 1024، 768، 430، 390.
- كان عنوان التشخيص بعرض نحو 12px بسبب توريث شبكة بطاقة الملخص إلى articles متداخلة.
- في 390px، بلغ ارتفاع الحاوية 432px بينما تجاوزت بطاقتا المعاينة معًا 510px؛ تداخل شريط الاعتماد مع البطاقة الثانية.
- مصدر الصندوق أسفل الأدوات هو `.manual-change-chart`، وليس `.selected-operation-panel` الذي كانت له قيمة `display: contents`. حجز الرسم 268–291px حتى دون مقارنة مفيدة. صار إفصاحًا اختياريًا يظهر بعد وجود مقارنة فقط، ولا يرسم أثناء إغلاقه.
- 20 حدث slider سريعًا كان ينتج طلبًا واحدًا بالفعل: لم يكن التكرار سبب هذه الحالة. لكن الاستجابة القديمة ظلت قابلة للقبول أثناء انتظار debounce، وكانت المعاينة المحلية تستخدم الصورة المعروضة، فتراكم أثر المسودة على نفسها.
- المعاينة الخادمية كانت تفك الأصل وتُصغّره في كل طلب. وفي السلسلة كانت تقرأ الأصل ثم النتيجة المعتمدة أيضًا. تحليل/Preservation كامل لم يكن يُنفذ في `/preview` أصلًا، وأضفنا اختبارًا يمنع إدخاله مستقبلًا.
- ملف `style.css` نفسه سليم. الخلل الحرفي `\\n` كان داخل `05-studio-a.css` و`06-panels-a.css` و`12-clinic-enhancements.js`. أصلحناه من المصدر. ملفات `static/css/parts` ليست ضمن سلسلة التحميل الحالية ولم نضف طبقة CSS جديدة.

## القياس القابل لإعادة التشغيل

البيئة: Python 3.13.14، OpenCV 5.0.0، NumPy 2.5.1، خيطا OpenCV. ثُبتت متطلبات المشروع قبل قياس المقارنة المعتمد.

```bash
PYTHONPATH=. python tools/benchmark_previews.py --baseline --output /tmp/preview-before.json
PYTHONPATH=. python tools/benchmark_previews.py --output /tmp/preview-after.json
```

أُعيد القياس في الجولة النهائية؛ `--baseline` يحمّل `app.py` من HEAD في الذاكرة دون checkout أو تعديل Working Tree، ويتحقق أن خوارزميات processing المتتبعة لم تتغير.

الصورة: `static/assets/document-before.png` مكبرة إلى 4200×2799، محفوظة JPEG في مجلد مؤقت. سبعة طلبات متتابعة لكل عملية؛ الوسيط للطلبات الستة بعد الأول. العميل Flask test client، لذا هذه أزمنة المعالجة/الاستجابة المحلية، وليست ضمانًا لزمن الإنترنت. العمليات تُشغّل بالتتابع على المصدر نفسه، ولذلك يشترك Sharpen وBilateral في cache المصدر الذي سخنته CLAHE.

- قبل الإصلاح: 7 قراءات/فك ترميز لكل 7 طلبات. بعده: قراءة واحدة للمصدر الصغير المشترك، وقراءة واحدة لنسخة التجهيز 1400px. تتلاشى النسخ من الذاكرة وفق TTL/LRU؛ قد تتكرر البداية الباردة بعد الإخلاء أو في عامل خادم مختلف.
- في profile التجهيز قبل الإصلاح، استهلكت GrabCut نحو 1.912 من 2.233 ثانية، وcalcHist نحو 96ms. لم نستبدل الكشف ولا نقلل دقته. لا توجد نسخة احتياطية موثوقة جرى اعتمادها للمقارنة؛ القياس المرجعي هو الإصدار الحالي قبل التعديل، وليس ادعاء مقارنة بإصدار قديم غير متحقق.
- بقي نقل JPEG داخل JSON/Base64 لتوافق API. يوجد ترميز واحد للمعاينة الجديدة، وليس ملف نتيجة نهائيًا. المعاينة العادية لا تكتب ملفات نتائج. تجهيز الوثيقة يحتفظ بملف مراجعة مستقل كما يتطلب عقد الاعتماد الحالي، وليس بنتيجة full-resolution.

الأرقام الخام وcProfile: `performance/preview-before.json` و`performance/preview-after.json`.

## ضمانات التنفيذ

- مصدر preview محدود 720×960، ومصدر Preparation محدود بأطول ضلع 1400، دون الاحتفاظ بالأصل الكبير في cache.
- مخزنان لكل تطبيق/عامل، كل منهما بحد 32MiB، مع TTL قدره 300 ثانية وحد عدد عناصر. توجد حماية single-flight للمفتاح نفسه؛ وتُفحص هوية الملف وحجمه وmtime/inode لتجنب مصدر قديم.
- الطلبات المتزامنة من الواجهة تُسلسل إلى عمل جارٍ وآخر تعديل مطلوب. تبطل صلاحية الاستجابة القديمة لحظة تعديل الإعداد، وليس بعد انقضاء debounce.
- rotate/flip ومعاينة القص محليًا على مصدر محدود ثابت. Gamma/Intensity خادميان لأن الخوارزميات الحالية تعمل على Lab luminance؛ تطبيق RGB في Canvas لم يكن مكافئًا. لم تتغير خوارزميات المعالجة.
- إحداثيات القص تُحوّل من الأصل إلى preview فقط؛ الاعتماد يستعمل إحداثيات الأصل ودقته الكاملة.
- حساب Preparation قابل لإعادة الاستخدام، لكن كل طلب يحصل على معرف مراجعة مستقل. رفض/اعتماد معرف لا يغيّر بقية المعاينات. الاعتماد يعيد معالجة الأصل.
- الرسم لا يستهلك Canvas/Histogram أثناء إغلاقه؛ عند فتحه يجمع تحديثاته في إطار واحد ويعيد استخدام Histogram المصدر الثابت.

## الاختبارات وحدود القبول

```bash
python -m compileall processing app.py
# node --check لكل ملفات static/js/parts
pytest -q
python tools/check_browser.py --output /tmp/browser-review
```

- قبل التعديل: 380 passed، 3 failed، 16 skipped.
- بعد التعديل: 395 passed، 3 failed، 16 skipped في 30.45s؛ الاختبارات المضافة الخمسة عشر ناجحة.
- سجلا pytest قبل/بعد موجودان في performance/pytest-before.txt وperformance/pytest-after.txt.
- الفشل الموروث لم تُغير اختباراته أو خوارزمياته: في c05 لم تُمنح أهلية الاقتصاص التلقائي؛ في c06 لا تنتج المعالجة مرشحًا صالحًا؛ وفي c08 التكرارية ثابتة لكن verification.verified يظل False.
- الاختبارات المتجاوزة تحتاج validation dataset غير مولّدة في المشروع. لا ندّعي تشغيلها.
- اختبار المتصفح اجتاز الأحجام الخمسة، مع صور طويلة 600×2600 وعلامة أعلى وأسفل، والوضعين الفاتح/الداكن. تحقق من أبعاد العناصر ومن نسبة الصورة واحتوائها وعدم تداخل الأدوات وشريط الاعتماد.
- 20 حدث slider سريعًا → طلب preview واحد، وصفر عمل histogram عندما يكون الرسم مغلقًا. rotate/flip ومعاينة تحديد القص لا ترسل POST؛ الاعتماد هو الذي ينفذ النتيجة.
- فُحص مدخل المعاينة السريعة القديم مباشرةً: طلب /preview واحد، بلا /operations، ومعرف النتيجة المعتمدة لا يتغير. أدواته القديمة غير موجودة في DOM الحالي؛ ليس سبب البطء المرئي الأساسي.
- اختبار فتح histogram ينتظر حالة الجاهزية الفعلية بدل مهلة 100ms الثابتة التي كانت تتسابق مع تحميل الصورة.
- لا أخطاء Console/JavaScript أو CSS/JS 404 في الجولة المختبرة، وآخر stylesheet محمّل ومقروء في CSSOM.
- نتيجة المتصفح المفصلة: `performance/browser-check.json`.

هذه ليست دعوى نجاح 100% لكل صور الاقتصاص: الحالات الثلاث المعروفة أعلاه ما زالت تحتاج معالجة منفصلة، ولا توجد Regression جديدة في الاختبارات الحالية. لم يتغير أي ملف لخوارزميات Morphology أو الكشف عن الميل والحدود.
